## 2. Current defect

Trace and confirm the current deployed path before editing:

1. `p2p_tcp.rs::read_loop` already knows `source_peer: NodeId`.
2. It sends only a bare `P2pMessage`, discarding that source.
3. `P2pInboundDemuxer` and `ChannelConsensusHandler` forward bare consensus messages.
4. `BinaryConsensusLoopIo` receives bare `ConsensusNetMsg`.
5. `handle_inbound_consensus_msg` derives `from` from:

   * `proposal.header.proposer_index`
   * `vote.validator_index`
6. An authenticated peer can therefore claim another validator index.

Record the exact on-disk source trace. Do not rely only on Run 417 line numbers because implementation edits will change them.

## 3. Required security behavior

Introduce an in-process, non-wire authenticated-origin envelope, or an equivalently strong typed design, carrying at least:

* full 32-byte authenticated `NodeId`
* authenticated `ValidatorId`
* decoded `P2pMessage` / `ConsensusNetMsg`

The origin fields must never come from the consensus payload.

Do not add the origin envelope to the serialized wire format. A peer must not be able to self-assert or overwrite it.

Propagate this origin from the successfully authenticated secure session through:

`TcpKemTlsP2pService read loop → subscriber → P2pInboundDemuxer → ChannelConsensusHandler → BinaryConsensusLoopIo → consensus ingress gate`

For the production-honest `MutualAuthMode::Required` + `pqc-static-root` path:

* require `mutual_auth_complete=true`;
* require both verified cert-derived validator identity and verified cert-derived client `NodeId`;
* use the exact verified `verified_client_node_id`;
* validate its association with `verified_peer_validator_id`;
* compare the pair against the configured authorized peer-cert mapping;
* reject missing, malformed, unknown, duplicate, ambiguous, or conflicting mappings;
* reject the connection or consensus ingress instead of assigning a temporary identity;
* do not derive a production NodeId solely from validator index;
* do not use self-asserted `client_random`;
* do not use self-asserted `ClientInit.validator_id`;
* do not use only the `vid@address` text without successful server-certificate/KEMTLS verification.

The authoritative mapping must use the complete 32-byte `NodeId`. Do not use the existing first-eight-byte `NodeId → PeerId(u64)` truncation as the security decision.

For outbound sessions, bind the peer identity established by successful server-certificate/KEMTLS verification to the configured validator. Refactor the secure-channel result if necessary to surface the verified server identity.

In Optional mode, only mutually authenticated peers may submit consensus messages. An unauthenticated Optional session must be rejected at consensus ingress.

Disabled-mode compatibility must not create a release-binary path where unauthenticated remote consensus messages are accepted. Any legacy compatibility adapter must be explicitly test-only or otherwise unreachable from the production consensus path.

## 4. Consensus ingress enforcement

For every currently handled message carrying an immediate sender claim:

* decode the message;
* determine the claimed validator;
* compare it with the authenticated transport validator;
* reject on mismatch before invoking the consensus engine or performing consensus-related side effects;
* on success, pass the authenticated validator to the engine as `from`, not a newly trusted payload-derived value.

At minimum enforce this for Proposal and Vote.

Apply the same rule to RestoreCatchup request/response or any other currently handled variant that contains an immediate sender identity. Do not invent a sender for a format that has no immediate sender field.

Timeout/NewView signature verification remains F5 and must not be claimed fixed merely because transport origin is now available.

For a rejected mismatch:

* do not call the relevant engine handler;
* do not record the proposal in the reconfiguration detector;
* do not mutate consensus state;
* do not create a vote, QC, timeout, new-view, restore response, or rebroadcast action;
* do not increment an “accepted/delivered” counter.

A raw inbound-message counter may still record that a frame arrived.

## 5. Mapping invariants

Build a validated one-to-one mapping:

* one full NodeId maps to exactly one ValidatorId;
* one ValidatorId maps to exactly one authorized NodeId for this configuration;
* duplicate validator entries fail startup;
* duplicate NodeIds assigned to different validators fail startup;
* malformed/out-of-range validator identities fail startup;
* an alternate root-valid certificate for the same validator but with an unconfigured leaf NodeId must not silently inherit the configured validator identity;
* no insertion may silently overwrite an existing conflicting mapping.

Use typed errors with bounded, non-secret diagnostic wording.
