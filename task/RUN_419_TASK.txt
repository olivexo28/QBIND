## 7. Required runtime scenarios

### S1 — Required/static-root honest control

Using validator 1’s valid configured certificate and KEM secret:

* establish real Required + `pqc-static-root` KEMTLS with the standalone validator-2 release node;
* prove an OS TCP socket was established;
* prove mutual authentication completed;
* prove the expected certificate-derived full NodeId/ValidatorId mapping was used;
* send one structurally decodable Proposal claiming validator 1;
* prove the live binding `accepted` counter increases exactly once;
* prove `claimed_sender_mismatch` does not increase.

The proposal may subsequently be rejected by current engine leader/view/signature rules. Record that separately. A binding acceptance is not a consensus-message signature verification or engine acceptance.

### S2 — Required/static-root authenticated impersonation rejection

Through a real KEMTLS session authenticated as validator 1, send structurally decodable frames whose immediate claimed sender is validator 0.

Cover every practical claimed-sender F6 branch:

* Proposal;
* Vote;
* Timeout;
* RestoreCatchupRequest;
* RestoreCatchupResponse.

If a branch cannot be constructed without changing production behavior, report that exact limitation and do not claim complete F6 runtime coverage.

For each frame:

* the payload must decode far enough to reach the F6 gate;
* the frame must be received through the real P2P/demux/binary loop;
* the binding decision must be `claimed_sender_mismatch`;
* exactly one bounded binding decision must be recorded;
* no delivered or engine-accepted counter may increment for that frame;
* no reconfiguration observation, view/state mutation or outbound consensus action may result from the rejected frame.

The aggregate expected mismatch delta must equal the number of tested claimed-sender frames. Ordinary network “received” counters may increase and must be reported honestly.

Use current-view/leader-shaped data where practical so the negative result is attributable to F6 rather than malformed decoding. Do not claim that unresolved F3/F4/F8 are fixed.

### S3 — Authenticated NewView origin admission

From a configured validator-1 Required/static-root session, send one NewView frame.

Prove:

* `authorize_origin` is reached on the standalone binary path;
* the binding `accepted` counter increases exactly once;
* no claimed sender is invented;
* the result proves transport-origin admission only.

Do not describe this as NewView signer verification. F5 remains unresolved regardless of the outcome.

### S4 — Optional unauthenticated ingress rejection

Start a fresh standalone receiver in Optional mode with the relevant static-root configuration. Connect a client that does not present a client certificate and send:

* one decodable Proposal;
* one NewView.

Prove:

* the session cannot obtain an authenticated consensus origin;
* `missing_origin` increases exactly twice;
* `accepted` and `claimed_sender_mismatch` do not increase;
* neither frame reaches its delivered/engine/state-mutation boundary.

### S5 — Disabled unauthenticated ingress rejection

Repeat the Proposal and NewView ingress test against a fresh Disabled-mode standalone receiver.

Prove the same fail-closed properties as S4. Disabled transport compatibility must not bypass the production consensus binding gate.

If the present transport configuration makes the real socket scenario impossible, report the actual behavior and leave this coverage partial. Do not substitute a manually constructed in-process envelope.

### S6 — Root-valid but unconfigured alternate leaf

Present a root-valid alternate leaf for validator 1 whose full certificate-derived NodeId is not the configured validator-1 NodeId.

Prove through a real socket that:

* root validity alone does not authorize consensus identity;
* no authoritative origin is produced for the unconfigured pair;
* a submitted Proposal is rejected before delivery/engine processing;
* the observed runtime reason is recorded exactly as implemented. Do not relabel `missing_origin` as `unknown_peer` if the resolver intentionally suppresses the unauthorized origin before the gate.

### S7 — Outbound actual-server identity check

Exercise the release node as an outbound dialer.

Configure an address as validator 0 with validator 0’s expected certificate, but have the listener present a different root-valid validator identity. If needed, use a test certificate with validator 0’s KEM public key but a different signed validator-id field so KEMTLS can complete far enough to exercise actual verified-server-identity comparison.

Prove:

* the dial address does not mint an authenticated origin;
* the actual verified server identity is compared with the configured authoritative mapping;
* the unexpected identity is refused;
* the connection is not registered as an authenticated consensus peer.

Do not use unreliable peer gauges as sole proof. Prefer the typed error/log result plus connection-registration evidence.

If S7 cannot be exercised without production changes or an unsafe general-purpose helper, record partial evidence and do not promote F6 to complete release-binary coverage.
