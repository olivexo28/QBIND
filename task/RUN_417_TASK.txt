## 1. Objective

Perform a source-to-runtime security reconciliation of QBIND’s foundational authentication boundaries before any durable public DevNet seed is provisioned or published.

Audit these four domains:

1. Transaction authentication and authorization.
2. Consensus proposal/vote/timeout/new-view authentication.
3. Consensus sender identity binding to the authenticated P2P/KEMTLS peer.
4. Quorum-certificate validation and production signature-suite enforcement.

This is an audit and evidence run. Its purpose is to establish what the current production binary path actually enforces, where it fails closed, where it remains incomplete, and whether existing documentation or readiness statuses overstate the implementation.

Do not implement the security fixes in Run 417.

## 5. Investigation A — transaction authentication

Determine and evidence:

1. Whether `verify_transaction_auth` accepts `tx.auths.is_empty()`.
2. Whether that behavior is reachable from any real transaction execution, block application, proposal, replay, restore, RPC, mempool, or peer-controlled path.
3. Whether all transaction types require authorization or whether narrowly defined system/genesis/bootstrap operations are intentionally exempt.
4. Whether exemptions are explicit and domain-separated, or whether empty authentication is accepted generically.
5. Whether keyset thresholds and key weights are enforced.
6. Whether duplicate signatures or duplicate keys can contribute weight more than once.
7. Whether the signer key must belong to the referenced keyset/account.
8. Whether the authenticated account is bound to the state mutation being authorized.
9. Whether transaction signing bytes bind at least the chain/domain, transaction body, nonce/replay field, fee/gas fields, and relevant authorization context.
10. Whether unknown suite IDs, missing keys, malformed signatures and unavailable keysets fail closed.
11. Whether tests explicitly depend on unauthenticated transactions and whether those tests represent production semantics or only fixtures.

Do not call empty-auth behavior remotely exploitable unless a real attacker-controlled ingress-to-execution path is demonstrated. Distinguish:

* verified fail-open behavior;
* verified but currently unreachable behavior;
* test/fixture-only behavior;
* fail-closed behavior;
* unknown/unproven behavior.

## 6. Investigation B — consensus message authentication

Trace the real binary construction and inbound processing of:

* proposals;
* votes;
* quorum certificates;
* timeout messages;
* timeout certificates;
* new-view messages.

For every message type determine:

1. Which identity is claimed inside the message.
2. Whether the outbound real binary signs it.
3. Which exact bytes and domain are signed.
4. Which suite ID is emitted.
5. Whether empty or placeholder signatures are emitted.
6. Whether inbound signatures are verified before engine acceptance or state mutation.
7. Whether the signer is a member of the active validator set.
8. Whether the signer is authorized for the claimed role and view.
9. Whether wrong-suite, unknown-signer, malformed-signature, replayed, cross-chain, cross-view and cross-message-type inputs fail closed.
10. Which production entry point performs each check.
11. Whether existing tests bypass transport identity or inject directly into an internal channel.

Treat comments such as “NOT FOR PRODUCTION,” default/toy suite markers, empty signatures, or uncalled verification helpers as evidence requiring runtime tracing—not as conclusions by themselves.

## 7. Investigation C — authenticated peer to consensus-sender binding

Establish the complete identity flow:

`KEMTLS handshake → authenticated certificate/peer identity → connection/session metadata → inbound P2P frame → ConsensusNetMsg → consensus engine sender identity`

Determine:

1. What KEMTLS actually authenticates: root, leaf key, NodeId, validator ID, or another identity.
2. Whether the authenticated identity remains attached to each inbound consensus message.
3. Whether `ChannelConsensusHandler` or another channel transmits peer/session identity with the message.
4. Whether the engine’s `from` identity comes from authenticated transport metadata or from self-declared `proposer_index` / `validator_index`.
5. Whether one admitted peer can claim another validator’s identity.
6. Whether the per-peer certificate override used in Run 416 establishes a durable validator-binding rule or only supplies handshake key material.
7. Whether reconnects, duplicate sessions, certificate reuse, or stale validator mappings can create identity ambiguity.
8. Whether connection authentication and consensus-message authentication are independent, complementary controls or whether either is incorrectly assumed to replace the other.

Do not claim that KEMTLS admission authenticates consensus authorship unless the binding is traced and enforced end-to-end.

## 8. Investigation D — quorum certificate and suite enforcement

Determine:

1. How a QC is created from votes.
2. Whether unique validator membership and quorum weight are enforced.
3. Whether duplicate votes can contribute more than once.
4. Whether the QC carries independently verifiable signer evidence.
5. Whether `signer_bitmap`, aggregate signatures or individual signatures are populated and validated.
6. Whether a QC received from a peer is cryptographically verified before it influences locking, view advancement, commit, restore or catch-up.
7. Whether proposal-carried parent/high QCs receive the same verification.
8. Whether timeout certificates receive equivalent validation.
9. Whether suite ID `0` is a toy/test namespace and whether it is reachable in the production binary.
10. How suite ID `0`, the observed Run 416 `sig_suite_id=100`, and any state/transaction suite identifiers relate or remain separate.
11. Whether unsupported, disabled, classical, dummy or ambiguous suite IDs fail closed in each security domain.

Do not equate the Run 416 transport-provider log with proof that consensus messages or transactions use the same signature suite.

## 9. Required threat-model cases

Evaluate at least:

* an authenticated malicious validator claiming another validator ID;
* an admitted peer replaying another validator’s signed message;
* an admitted peer sending an unsigned or empty-signature proposal/vote;
* duplicate votes or duplicated signer entries inflating quorum weight;
* a forged QC or timeout certificate;
* wrong-suite and unknown-suite messages;
* cross-chain, cross-view and cross-message-type signature reuse;
* a transaction with zero authentication entries;
* signatures below the keyset threshold;
* duplicate transaction signatures contributing repeated weight;
* an authorized signer attempting an unrelated account mutation;
* restore/catch-up importing insufficiently authenticated consensus evidence.

For each case state the attacker prerequisite, entry point, enforced checks, resulting behavior, exploitability and confidence.
