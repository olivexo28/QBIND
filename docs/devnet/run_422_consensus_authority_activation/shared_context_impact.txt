============================================================================
CONSUMERS AFFECTED WHEN verification_ctx BECOMES Some
============================================================================

When Run 422 supplies a Some context (valid genesis-bound DevNet activation),
the following consumers gain cryptographic verification/signing — IDENTICALLY to
the pre-existing CLI activation path:

  1. Inbound Proposal   -> signature + suite + F6 sender-binding verification
  2. Inbound Vote       -> signature + suite + F6 sender-binding verification
  3. Inbound TimeoutMsg -> verify_timeout_msg (view/block-id/sender binding)
  4. Inbound NewView / TimeoutCertificate ->
       verify_timeout_certificate_with_evidence (per-signed-timeout membership +
       signature checks)
  5. Outbound TimeoutMsg -> signed by the configured local signer before emit
  6. Locally-formed TimeoutCertificate -> signed_timeouts attached

This is the DOCUMENTED, intended scope of the shared context. It is NOT a new or
out-of-scope activation: the same widening already occurred whenever the Run
031–033 CLI path produced a Some context. Run 422 only re-sources the authority.
