THE GAP (pre-Run-422)
============================================================================

Runs 031–033 activated a consensus verification/signing context on the
standalone binary, but sourced the validator consensus keys from the
UNCOMMITTED CLI surface:

  crates/qbind-node/src/main.rs
    build_validator_set_and_key_provider(config, local_validator_id, ...)
      -> reads config.network.static_peer_consensus_keys
         (populated ONLY by `--validator-consensus-key VID:SUITE:HEXPK`)
  crates/qbind-node/src/peer_key_provider.rs
    LoadedValidatorKeyProvider / build from static_peer_consensus_keys

Problem: an uncommitted local override cannot define network authority. Two
operators can each pass a different `--validator-consensus-key` set and both
"activate" against unrelated key material, with no cryptographic tie to the
network they claim to join. (Recorded in repo memory as the "abuse/DoS wiring"
and Run 031–033 context.)

Meanwhile, the canonical authority ALREADY EXISTS in genesis and is ALREADY
boot-verified but was never wired into the runtime key provider:

  crates/qbind-ledger/src/genesis.rs
    GenesisValidator.pqc_public_key   (ML-DSA-44, "the validator's signing key
                                        for consensus operations")
    GenesisConfig.validators : Vec<GenesisValidator>
    compute_canonical_genesis_hash(...)
  crates/qbind-node/src/pqc_boot_genesis.rs
    run_boot_time_genesis_verification(...)  (loads external genesis, computes
      canonical hash, enforces --expect-genesis-hash pin)
  crates/qbind-node/src/pqc_authority_state.rs
    data-dir authority marker pins the accepted genesis/network identity.

So the genesis-committed per-validator consensus key was verified at boot and
pinned to the data dir, yet the runtime consensus key provider ignored it.

============================================================================
THE FIX (Run 422, Route A)
============================================================================

New module crates/qbind-node/src/genesis_consensus_authority.rs:
  build_genesis_consensus_authority(&GenesisConfig, &GenesisHash, ValidatorId)
    -> GenesisConsensusAuthority { validators: ConsensusValidatorSet,
                                   key_provider: Arc<dyn
                                     SuiteAwareValidatorKeyProvider>,
                                   genesis_hash, chain_id, commitment:[u8;32],
                                   validator_count, fingerprints }
  * maps genesis validator vec index i -> ValidatorId::new(i);
  * decodes each pqc_public_key with the strict hex decoder reused from
    peer_key_provider::decode_strict_hex_pk;
  * enforces suite == SUPPORTED_TIMEOUT_SUITE_ID (ConsensusSigSuiteId(100),
    ML-DSA-44) and key length == ML_DSA_44_PUBLIC_KEY_SIZE (1312);
  * rejects empty set, count > MAX_GENESIS_CONSENSUS_VALIDATORS (4096),
    malformed/oversized/short keys, duplicate keys, duplicate addresses,
    local-validator index out of range, ConsensusValidatorSet::new failure;
  * computes a domain-tagged commitment:
    sha3_256_tagged("qbind.run422.genesis-consensus-authority.v1", body)
    where body length-prefixes chain_id, appends genesis_hash (32B), the
    validator count, then per-validator (index, suite, pk_len, pk).
  * reads ONLY GenesisConfig.validators[].pqc_public_key — never transport
    roots or bundle-signing roots (authority separation).

Wiring, crates/qbind-node/src/main.rs: the SINGLE early startup guard (before
`match config.network_mode`) refuses --consensus-authority-from-genesis with
exit code 1 across all modes/environments. The downstream Run 422 block (behind
`if args.consensus_authority_from_genesis` inside run_p2p_node) still contains
the fail-closed resolution (external genesis required, single-snapshot
load/verify/build, signer required, signer<->genesis key match) feeding the SAME
try_build_timeout_verification_context, but that block is UNREACHABLE now because
