## Source observations

`crates/qbind-net/src/transport.rs:49-67` is the unchanged public decoder. It
returns `Protocol("transport frame too short")` when fewer than five header
bytes are present. It reads a big-endian `u32` length as `usize`, checks
`buf.len() < 5 + len`, then copies `buf[5..5 + len]`. With a representable
endpoint, an undersized payload returns
`Protocol("transport frame payload truncated")`. A complete frame decodes
normally. Bytes after the declared payload are ignored because the decoder
copies only the declared range and does not require the buffer to end there.

On targets where `usize` is wider than 32 bits, `5 + u32::MAX` is representable;
the new header-only maximum-length test therefore expects the existing
truncation error. A 32-bit target can represent `5 + (usize::MAX - 5)`, but not
the endpoint for larger declared lengths. Inspection shows the current checked
comparison and later range expression both use unchecked `5 + len`. The
32-bit ignored witness expects a normal truncation `Err`, so the baseline's
overflow/panic behavior is not misreported as a pass. No native 32-bit run was
available to observe it.

Established production call paths:

- `crates/qbind-net/src/framed_io.rs:113-140`, `read_transport_frame`, reads
  the header, rejects lengths above `MAX_TRANSPORT_CIPHERTEXT` (16 MiB) before
  allocating/reading the body, then calls the decoder. This limit belongs to
  the stream reader, **not** to the public decoder.
- `crates/qbind-net/src/connection.rs:403-430`, public `Connection::decrypt_app`
  directly calls `TransportFrame::decode(frame_bytes)` without its own frame
  size limit.
- `crates/qbind-node/src/secure_channel.rs:524-532`, the send path encrypts
  and encodes via `Connection::encrypt_app`, decodes its own generated bytes
  into a frame, then writes the frame.
- `crates/qbind-node/src/secure_channel.rs:547-575`, the receive path uses
  `read_counted_frame`, which calls the capped `read_transport_frame`, then
  re-encodes that frame and passes it to `Connection::decrypt_app` (which
  decodes it again).

These are source-visible routes, not evidence that an anonymous remote peer can
reach an uncapped decoder with arbitrary input. The test host/target was
`x86_64-unknown-linux-gnu`; no deployment target, deployed binary, or running
node was established by this task. No anonymous remote exploit or deployed
impact is asserted.
