BOUNDARY DEFINITION USED BY THE D4 TESTS
----------------------------------------------------------------------------
  "Fatal consensus-security preflight failures occur before P2P SERVICE
   CONSTRUCTION (builder.build at 7511), peer dialing, and consensus-task
   startup."

  A negative D4 case is accepted only when ALL hold:
    (1) nonzero exit;
    (2) the expected preflight diagnostic/positive-control marker
        ("[binary] Run 032:" or "[binary] Run 033:") IS present — proving the
        input reached the preflight, not a CLI-parse or unrelated earlier
        failure;
    (3) the post-build marker "[binary] P2P transport up." is ABSENT.
  Absence of (3) alone is never treated as sufficient.

  The positive D4 case additionally requires "[binary] P2P transport up." AND
  "timeout verification ACTIVE" to be present with NO refusal — proving the
  valid legacy configuration passes preflight and reaches P2P startup with a
  live Timeout context while PV authority stays absent.

THE METRICS EXCEPTION (EXPLICIT)
----------------------------------------------------------------------------
  Because the optional metrics HTTP server is spawned at main.rs:4643 —
  earlier than run_p2p_node and its preflight — the D4 result MUST NOT be
  described as "before any networking", "before all listeners", or "before
  every service".

  * The metrics HTTP task is loopback/opt-in (QBIND_METRICS_HTTP_ADDR) and is
    unrelated to consensus admission or signing.
  * It was NOT moved in this run; no unrelated metrics/storage startup was
    relocated to strengthen wording.
  * The preflight function itself (5019-5551) starts NO network service.

  D4 scope label: PRE-P2P-AND-CONSENSUS-PREFLIGHT (preflight before P2P
  service construction, peer dialing, and consensus-task startup), WITH the
  optional metrics HTTP task acknowledged as started earlier.
