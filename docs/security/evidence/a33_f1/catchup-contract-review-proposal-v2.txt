1. Precise current engine behavior and effect order

Source locations below are in 38a0180 unless explicitly qualified:

1. `basic_hotstuff_engine.rs:3954-3970`: an empty response returns Ok(0);
   otherwise local committed height/block seed the expected next height and
   parent, and prior_qc is copied from current lock. If no committed anchor
   exists, return MissingLocalAnchor before mutation.
2. `:3972-4016`: for each item in sequence, contiguous height, exact parent,
   height==view, scheduled proposer, deterministic block id, then logical
   QC validation run before this item mutates engine state. The logical QC
   validation proves configured membership, distinct signers and quorum
   voting power; it does not verify signatures (A17-F1 remains open).
3. `:4018-4024`: `state.register_block` is called before this item's signer
   replay. At the state layer `hotstuff_state_engine.rs:1455-1488`, height is
   calculated using the currently resident parent (missing parent => height
   zero); an existing id replaces the entire node, while a new id is queued;
   then legacy best-effort eviction runs. Replacement resets the node's
   `own_qc` and verified justification, and retained byte accounting releases
   the replaced node's charge via `insert_block_node`; a replacement is not
   queued again. If no safe block exists, registration returns normally with
   the new id resident and the tree over `max_pending_blocks`.
4. `:4025-4030`: for each supplied signer, `state.on_vote` is invoked. In
   `hotstuff_state_engine.rs:1639-1671`, vote history is examined/mutated
   first: a new membership may evict old vote-history views and insert
   `(view, validator)->block`; conflicting prior history records equivocation
   and suppresses accumulator insertion. For first/duplicate-same history,
   `:1751-1792` passes through `VoteAccumulator::on_vote_detailed`; it may
   evict old accumulator views, insert/duplicate/drop a vote, or return
   NonMemberSigner. CapacityDropped is Ok, increments dropped-vote count,
   and does not stop the signer loop. `maybe_qc_for` may return no QC, a QC,
   or a QC-validation error. A produced QC is synchronously sent to `on_qc`
   at :1703-1714.
5. `on_qc` at :1794-1819 updates the lock first if the QC view is higher,
   sets the block's own_qc if the node remains resident, then attempts
   fixed-depth 3-chain commit. The current implementation's `on_qc` returns
   Ok after these effects. `try_commit_with_qc` at :1822-1927 has no
   recoverable error return; it either updates committed block/height/log
   according to existing predicates or returns without commit.
6. Only after every signer loop returns Ok does catch-up replace previous_qc,
   advance local expected parent/height and increment local `applied`
   (:4027-4030). Only after all response items does it call `set_view`
   (:4034-4036). `applied` is returned only on complete response success.
   Any error returns `Err(RestoreCatchupError)` without the local completed
   prefix count; no rollback restores a prefix, a current registered block,
   signers, QCs, lock, commits, evictions/accounting or history. Error skips
   final view advancement.

Within-item error boundary:
- The only ordinary `on_vote` error is NonMemberSigner. It is checked by the
  accumulator after vote-history work. Because this same item first passed
  `qc.validate` against the same immutable validator set and iterates that
  unchanged distinct signer vector, this error is not expected for an
  invariant-consistent execution. No normal callback mutates validators
  between these stages. `on_vote_detailed` still calls
  `reconcile_received_vote_evidence` after the vote result, including an
  error; this may prune received-vote evidence memberships and associated
  accounting, so a partial-current report must include that reconciliation
  effect too.
- `maybe_qc_for` can surface a QC validation error after accumulator insertion;
  under normal invariants its signers came from validated member votes. This
  too is not expected, but if it occurs, that vote's history/accumulator
  effects have occurred, then received-vote evidence reconciliation runs;
  earlier signers in the same item may have formed/applied QCs and commits.
- No `on_qc` recoverable failure exists after its lock/own_qc/commit effects
  in this implementation. Do not fabricate a rollback/error stage there.
- An equivocation or accumulator CapacityDropped is not an error. Catch-up
  continues, increments `applied` for the item after all listed signers, and
  can return Ok even if some supplied signers did not add accumulator weight
  in this pass. If old accumulator votes suffice, `maybe_qc_for` can still
  form/apply a QC.

Thus a future typed catch-up result cannot safely label only “N complete
blocks” as the entire effect summary when an unexpected signer-stage error
occurs: the current block is already inserted/replaced, earlier signers may
have changed history/accumulator/QC/lock/commit, and registration may have
evicted nodes and reclaimed their evidence; the failing `on_vote` also
reconciles received-vote evidence. Conversely, capacity refusal
placed before registration and signer replay can guarantee **zero effects
for the rejected new item**, while preceding completed items may remain.

2. Admission/capacity and replacement cases

The corrected `can_admit_block_slot` / `reserve_block_slot_for_new` in
`hotstuff_state_engine.rs:896-984` are appropriate source mechanisms for a
catch-up new-id preflight, but `register_block` does not call them:

- Below capacity (`block_count < max_pending_blocks`): current code can add
  one new id without eviction. A new cap contract may continue this.
- At capacity: one safe-to-evict other node is enough. An indeterminate
  (cycle, absent locked/QC ancestor, exhausted traversal) candidate is not
  safe and cannot be selected. If no safe slot is available, owner direction
  requires refuse before inserting the new item or replaying its signers.
- Already above capacity: a hard cap needs `current + 1 - max` safely
  evictable other nodes before a new item, not just one; if the full deficit
  cannot be met, refuse that new item without further eviction or insertion.
- Safe acyclic candidates: preserve present eviction ordering, pre-eviction
  height, exact removal accounting, counters and QC/lock/committed/ancestor
  protections. Review whether reserve's fallback ordering is acceptable for
  catch-up; it differs from pending queue ordering if that queue is incomplete.
- Existing id: current slot query treats it as admissible with no new slot.
  But catch-up replacement resets own_qc/verified evidence and may rewrite
  `parent_id`/height/justification, alter ancestry, reclaim evidence bytes,
  preserve but not re-add its pending-order position, and then replay votes.
  A full-map replacement therefore is not a no-op and can weaken retained
  protection. Direction 1 is explicitly for a **new** block; it does not
  authorize arbitrary existing-id replacement. A reviewed policy must choose
  among: (a) allow only a demonstrably idempotent matching replacement,
  (b) refuse any replacement while catch-up is unresolved, or
  (c) define a separately justified replacement transition. Current source
  has no such equivalence/identity predicate; equality of derived 32-byte id
  alone is insufficient proof of identical full parent or node state.

`register_block` is also called by ordinary Proposal paths
(`basic_hotstuff_engine.rs:4095,4703`) and leader proposal creation
(`:4088-4097`). Applying a hard cap to all legacy registration is a separate
open scope per owner direction. A catch-up-only refusal would not justify
claiming a system-wide limit; unrelated legacy calls can retain over capacity.

3. Catch-up result and node caller contract candidate

Current `RestoreCatchupError` (`basic_hotstuff_engine.rs:1939-1969`) has no
capacity variant, prefix count, current-item phase or effect report. Its
existing errors arise before mutation of the *current* item, but can follow
prior applied items. A future result should distinguish at least:

- clean refusal/rejection: no current item mutation; completed prefix count
  and prefix effects still reported if nonzero;
- capacity refusal before a new item: rejected index/id, completed prefix,
  no insertion/vote/eviction for that current item;
- current-item error before registration: zero current-item mutation;
- current-item signer-stage error after registration: current item registered
  or replaced, attempted/replayed signer boundary, completed prefix count,
  and explicit partial-current effects; no false “current block not applied”
  or “no mutation” claim;
- complete success: fully processed item count and existing normal final-view
  behavior.

Proposed compact typed envelope, shape only (not an API decision):
`CatchupApplyReport { completed_items, outcome, current_item_effects,
pre/post_committed_anchor, pre/post_lock, pre/post_view, retained_bytes_delta,
evicted_ids_or_count, view_advanced }`, with `outcome` distinguishing
Complete, RejectedBeforeMutation, CapacityRefused, and FailedDuringItem.
The current stage/effect fields must be populated from actual mutation
boundaries, not reconstructed from the error enum after the fact. Include
block id/index, whether registered/replaced, signer-attempt count, vote
history/accumulator dispositions (including conflict/capacity-drop),
QCs applied, and commit/lock changes if needed to identify effects. If
capturing exact objects is too costly, document the narrower guarantee:
state snapshot/delta can be queried by caller while engine is exclusively
borrowed, and result marks current item as mutated/partial. Do not infer the
results only from whether `Err` was returned.

At `binary_consensus_loop.rs:8437-8506`, current Ok adds `applied` counter and
evaluates peer-target/restore-mode exit; current Err increments only rejected
responses, skips target tracking and mode evaluation, and contains an
inaccurate no-mutation comment. The corrected handler must:
1. log/status the typed outcome and prefix/current-item effects truthfully;
2. account completed prefix blocks even when the response terminates with
   capacity refusal/error, without conflating response rejection and applied
   prefix;
3. not treat the peer-reported height as usable progress from an unresolved
   partial response;
4. set a sticky unresolved-catch-up condition before another normal effect
   can execute, unless the approved reconciliation result explicitly clears
   it; and
5. specify the exact outbound-request/response retry anchor, application
   ordering, inbound proposal handling, local leader/vote/timeout/QC behavior,
   metrics and exit transition while unresolved.

Current restore mode is not itself a full participation freeze. It sends
requests based on the current committed pair (`binary_consensus_loop.rs:
8350-8370`), defers only certain future/wrong-parent proposals
(:8372-8392, :6571-6595), and suppresses view timeouts while active
(:2435-2448); it does not encode a partial-application checkpoint. On an
error the handler remains active and does not feed responder height to the
tracker, but a committed prefix can already have changed the local anchor.
`current_view` is not set by the catch-up function on that error; later
ordinary Proposal handlers and other consumers may still mutate engine
state. The requirement to prevent resumption therefore needs a defined
gate/state-machine integration, not the existing active bit alone.

5. Concrete alternatives requiring decision

A. Prefix-preserving pause and resume:
   Keep completed effects. Return prefix/current-stage report and a sticky
   incomplete status. Choose a safe reconciliation algorithm that accounts
   for committed advancement, uncommitted nodes and votes, replacement
   semantics, view, request anchor, retry index and all normal event gates.
   Resume only after this state machine has a reviewed, testable transition.
   This is aligned with owner direction but not yet sufficiently specified
   to code safely.

B. Reinitialize/recover after partial effects:
   Quarantine normal operation and rebuild from an explicitly trusted
   committed checkpoint. Must handle a prefix that already committed: a
   restart cannot discard durable/committed advancement. Requires approved
   snapshot/anchor provenance and durable/volatile state correspondence;
   not currently established by this task.

C. Stage and atomically publish a complete response:
   Validate all structure first, then stage all block, history, accumulator,
   QC, lock, commit, evidence and view effects in an isolated state and swap
   only after complete success. This is a substantial new transactional
   mechanism and still requires an approved policy for capacity, replacement,
   memory overhead and externally observable effects. Current source provides
   no rollback/transaction; do not claim that syntax prevalidation alone
   implements this alternative.

D. Explicit resumable item/signer cursor:
   Preserve prefix and current-item partial effects, persist a cursor plus
   exact current state identity, and replay only remaining work after
   revalidation. Must define duplicate/equivocation behavior, QC idempotency,
   replacement, crash/restart persistence, and signer-level failure. No such
   cursor or durable state correspondence exists today.

Required owner/contract decision is therefore not merely “hard cap or not.”
It must select a partial-state recovery alternative and specify the safe
resume gate, replacement semantics, report shape and node caller behavior.
Until then, implement only the already landed finite eviction walks; no
catch-up source/test behavior is changed by this proposal.
