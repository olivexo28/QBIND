# A33-F1 / E27 initialization, binding and continuity contract

**DESIGN PROPOSED — INDEPENDENT REVIEW PENDING.** This amendment supplements, and does not supersede, the [storage candidate](storage-candidate-design.md) and [stay-closed contract](stay-closed-contract.md). It does not approve an implementation, persistent format, initialization ceremony, durability profile, recovery authority or transition to participation. A33-F1 / E27 and other unresolved obligations remain **OPEN**; activation **DISABLED**; public DevNet **NO-GO**.

The author considered the owner-supplied review of candidate commit `83ec48cf37d71c53d4e623b7a9ff8227f0008250`: existing-only open can still have effects; the checked object must own the boundary; filesystem claims must name the threat model; and capacity must include the complete cumulative encoding. These are user-supplied observations, not a newly performed independent review. The previously reported Python temporary-directory controls are local, non-independent observations; no standalone raw artifact was retained in the repository. They do not prove Rust-backend behavior, power-loss durability or record-capacity sufficiency. No numerical pass count from those controls is used as backend evidence.

## 1. Threat model and non-negotiable boundary

The candidate is a local external marker and a separate consensus store. It assumes a specifically identified operating system, filesystem, mount, device and process-ownership profile, and cooperating node processes which use the same destination lock. Hostile local actors, privileged administrators, filesystem implementations, devices or other processes that can replace lock files, mount points, database paths or storage content are not automatically fenced by that lock. State the exact permissions and operational exclusions in a separately reviewed deployment profile. If those assumptions cannot be established for a path, the participating path refuses; do not claim universal protection from held descriptors or successful equality checks.

Neither marker checksum, file identity, lock, database metadata, copied record nor an `Arc` establishes freshness, chain authority or exclusive signing. The separately trusted currentness and signer-exclusivity authorities remain undecided. A valid local record, successful initialization or matching pair is not a participation, signing, recovery or clear permit. No ordinary startup may create a missing baseline or treat a missing marker, database, lock or metadata as a fresh history.

## 2. Existing code is precedent, not this boundary

At the pinned candidate revision, [`acquire_destination_lock`](../../../../crates/qbind-node/src/restore_completion.rs) opens a lock by pathname and allows creation. [`RocksDbConsensusStorage::open`](../../../../crates/qbind-node/src/storage.rs) enables `create_if_missing`; the [production lifecycle](../../../../crates/qbind-node/src/production_consensus_storage.rs) creates the parent when absent and performs schema/epoch checks. Their existing behavior cannot be reused as evidence of existing-only inspection or stable identity binding. The restore record reader uses final-component no-follow and bounded reads on Unix, and its publisher syncs and renames, but those properties do not establish parent-path confinement or the new marker protocol.

In particular, `create_if_missing(false)` does not establish that a database open is read-only or effect-free. Recovery, lock acquisition, log or metadata writes, and library/platform behavior must be inventoried from the actual chosen open mode and tested under a named profile. Before chain/store metadata is checked, only separately reviewed opening effects needed to inspect the candidate are permitted; no application-level consensus, restore, epoch, signing or catch-up mutation is permitted. If a safe open mode and its effects cannot be established, refuse before opening. On mismatch or uncertain open effects, stop, preserve available diagnostics, retain quarantine and do not repair, rewrite identity, retry through another path, materialize restore, start services or claim the store was untouched. Opening effects already incurred must be reported as such.

## 3. Initialization is separate and remains closed

Fresh provisioning and legacy migration are distinct, separately authorized and reviewed administrative procedures; neither is executed by ordinary node startup. A procedure must first establish the chain/genesis identity, the input store and its provenance, exclusive local ownership, operator authority, initialization intent, and the complete candidate metadata and marker version. An absent marker cannot distinguish a new destination from deleted or rolled-back history. A legacy database with no marker is not a clean database. Unknown provenance, already-used signing history, existing unexpected data, ambiguous partial initialization or identity uncertainty refuses rather than being reset.

The detailed persistent encoding, initial-record states, actual identity allocation/non-reuse rule, migration workflow and fsync profile are **not selected here**. Any candidate must specify a failure-closed cross-store ordering. At minimum: (1) establish and retain destination/marker ownership without inventing missing baseline artifacts; (2) create or inspect the database only within the separately authorized initialization transaction and write any new DB binding under its explicitly reviewed acknowledged durability protocol; (3) publish and acknowledge a marker bound to that exact DB binding under the marker profile; (4) retain a typed closed result, not a participation permit. Steps may be revised only by a separately reviewed ordering proof covering every crash boundary.

Because the database and marker do not share an atomic commit, partial results are expected. Missing marker with DB metadata, marker with absent/mismatched DB metadata, unacknowledged writes, lost acknowledgement, unknown state or repeated initialization must all remain closed and preserve diagnostic evidence. Recovery/repair of such a pair requires a separate reviewed procedure; do not automatically create the other half, overwrite, delete, treat a matching copy as current or resume. Syncing one store does not acknowledge the other. Even a fully acknowledged pair is only a local binding and remains closed until distinct startup and authority decisions are approved.

## 4. Binding and ownership: proposed enforcement

The candidate checked binding should be constructed only by a private, fallible constructor after the relevant ownership is held and the marker and DB identities are checked. It owns or controls the lifetime of: (a) the trusted-root and marker-directory handles used for relative no-follow operations; (b) the stable lock descriptor and its acquisition; (c) the exact already-open database capability; and (d) the active operation owner and admission/barrier state. Identity is obtained from the inspected marker and the exact DB capability, not supplied anew by a caller after checking. The exact chain/genesis, store/incarnation, operation, revision and owner fields, bounds and authentication remain proposed inputs to later format review.

An API sketch is an ownership obligation, not compilable code: `CheckedStore::open_existing_owned(...) -> Result<ClosedCheckedStore, Refusal>`, followed by operation-scoped methods such as `begin_applying(&mut self, barrier, intent)` and `record_outcome(&mut self, ack, update)`. `ClosedCheckedStore` has private fields and no constructor from raw path strings, caller-asserted identity, a deserialized token or a boolean barrier. All handles shared with the catch-up mutation path must come through capabilities constrained by the same owner. An unrestricted DB handle with mutation methods handed to unrelated callers would bypass this boundary; either eliminate/mediate that route or demonstrate a complete owner/barrier inventory that makes it unreachable during the guarded operation. No such enforcement exists today.

If sharing is necessary, clones refer to the same in-process ownership and revocation state, not newly acquired independent locks or independently minted authorization. Define a single coordinator, serialization and cancellation semantics; clones may not continue after shutdown, lost ownership, binding failure or owner revocation. A clone's existence must not keep authorization alive after revocation. During orderly shutdown the owner retains the lock and root/marker handles until guarded operations are stopped or fenced and completion is observed; unobserved work remains Unknown and quarantine remains closed. Closing an FD or dropping an `Arc` is not proof that an already admitted signer, storage task or network worker stopped. Process death releases local descriptors and locks even if external work continues: the design must retain the pre-existing durable closed state for restart and separately address external signer fencing and unresolved effects; it cannot promise to retain a process lock after a crash. A restore replacing the DB, parent, marker or identity invalidates the checked binding: stop before effects, and require separate reviewed migration/rebind rather than reopen by path.

An opened DB must be proven to correspond to the object inspected and kept for guarded mutations. Process-local pointer equality or path-string equality is insufficient to prove object identity or continuity. The design must establish how the selected DB API actually opens the object relative to held directories and how a replacement during open is excluded or detected *before protected effects*. If the RocksDB API cannot establish this under the selected threat model, the supported design must impose and verify an explicit filesystem-control assumption or refuse the configuration; a pre-open stat and later pathname reopen alone are not proof. Rechecking identities is a control only within its stated race and attacker assumptions.

## 5. Replacement and loss cases

| Event | Required disposition and limit |
|---|---|
| Parent or marker-directory rename/replacement | Directory-relative operations use the held object, but that alone does not prove another component used the same destination. Bind all participating components or refuse; if adversarial replacement cannot be prevented/detected before effects, exclude it explicitly in the approved profile. |
| Lock-file unlink/replacement | A lock on an old inode need not lock its replacement. Cooperating participants must share a stable lock object; inability to enforce or detect replacement before effects is an explicit unsupported threat or refusal, not a cross-process fencing guarantee. |
| Database pathname swapped before/during/after open | Path equality or a metadata label alone is insufficient. Prove object continuity for the actual API under the approved assumptions; otherwise refuse. Existing handle ownership does not make later pathname users safe. |
| Ownership or handle loss; shutdown/cancellation | Revoke mutation admission, retain ownership until guarded work is observed completed/fenced, and record known or Unknown outcomes. Do not claim cancellation or shutdown request completed that work. |
| Restored or copied old matching pair | Readable/matching records do not establish currentness or signer exclusivity. Stay closed pending separate authority and reconciliation. |

## 6. Full record capacity and uncertainty

The candidate's **65,536-byte ceiling is unapproved and unproven**. Derive a checked worst-case bound for the complete encoded representation, not a payload alone: envelope/tag/version/lengths, chain/store/incarnation/operation/owner/revision bindings, anchors and response identity, per-item prefix/current effects, all signer/storage/snapshot/epoch/callback/outbound observations, conflict and Unknown representations, cumulative updates, any indexes or padding, integrity field and all framing. Include maximum entry counts, maximum entry sizes, duplicate/retry policy and overflow-safe arithmetic. Map each count and byte bound to an enforceable producer constraint; account for actual supported response limits and aggregate effects over the entire operation. Unknown or unbounded contributions mean 65,536 bytes is not established. Do not set a limit by assumption or silently discard data to fit.

Reserve sufficient supported capacity before admitting work when possible, including for effects that may be reported later. Preflight cannot prevent already admitted asynchronous work from completing or an unexpectedly large result from arriving. On late oversized/unsupported outcome, recognized active ownership latches before validation; preserve the complete input with its caller/owner and label it **unrecorded**, not durable or no-effect. Do not truncate or let a smaller retry erase it. A crash can lose caller-held evidence: the earlier acknowledged Applying record is intended to keep restart closed, but it cannot reconstruct the lost effect. Any alternative bounded evidence store or further admission rule needs separate review.

## 7. Acceptance cases — required, not run

| Case and layer | Observable acceptance condition |
|---|---|
| Fresh/legacy initialization, marker/DB half-created; unit + filesystem + later binary | Every incomplete, missing, conflicting or uncertain pair refuses, without automatic recreation, identity rewrite, clear or participation; log exact permitted opening effects. |
| Existing-only database open, unavailable/foreign identity; backend integration | Document observed file/database effects for the chosen configuration; mismatch stops before protected effects; do not assert a failed open was effect-free. |
| Parent, marker directory, lock file and DB path replaced around open/use; filesystem integration with controlled cooperating and adversarial fixtures | For each race, show prevention or detection before protected effects under the named platform; otherwise show explicit unsupported-profile refusal. Do not generalize to actors outside the stated threat model. |
| Same held binding, clone, revoke, shutdown and restore replacement; owner/API integration | No raw mutation bypass; owner state shared; loss/revocation fences new work; unknown in-flight work stays owned; replacement requires separately reviewed rebind. |
| Intent and outcome write/file-sync/rename/directory-sync failures; filesystem failpoints | No acknowledgement for failed/uncertain stage; visible-after-error is not durable success. Pre-rename old-record claims only when the stage is established. |
| Complete format at exact bounds, one byte/count over, integer overflow, cumulative histories and late effect; codec + owner integration | Check whole encoded size and producer maxima; refuse safely without truncation, preserve owner-held rejected data as unrecorded, no mutation reauthorization. |
| Interrupted acknowledged intent, each initialization publication boundary, and restart; separately scoped process/binary | Startup refuses before enabled metrics, signer, network, restore mutation and consensus. Process-kill results do not establish power-loss behavior. |
| Power-loss profile and stale copied pair; separately scoped storage/system controls | Claims limited to the tested declared stack; valid old copies cannot establish currentness, and local locks cannot establish exclusive signing. |

All cases above are proposed, not executed. No production source, tests, startup gate, signer, network, automatic clear, live node, signing or deployment is authorized by this amendment. Independent review and concrete backend/initialization acceptance remain pending.
